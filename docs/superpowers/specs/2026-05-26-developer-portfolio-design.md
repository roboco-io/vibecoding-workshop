# Design Spec: 개발자 바이브 코딩 워크숍 포트폴리오 랜딩페이지

> 작성일: 2026-05-26 | 작성자: ROBOCO | 상태: v2 (Codex 리뷰·사용자 새 프레이밍 반영)

## 1. 개요

### 1-1. 목적

개발자 바이브 코딩 워크숍을 외부 고객(엔지니어링 매니저·CTO)에게 소개하고 **도입 문의를 유도**하는 HTML 포트폴리오 랜딩페이지를 제작한다. 비개발자 트랙 페이지([roboco.io/vibecoding-workshop/.../vibecoding-for-nondeveloper/portfolio/](https://roboco.io/vibecoding-workshop/vibecoding-for-nondeveloper/portfolio/))와 동일한 시각 시스템·구조를 공유하되, 콘텐츠와 메인 프레이밍은 개발자 트랙의 가치 명제에 맞춰 새로 설계한다.

### 1-2. 청중과 목표 행동

| 항목 | 정의 |
|------|------|
| 1차 청중 | 엔지니어링 매니저·개발팀장 (팀 도입 결정자) |
| 2차 청중 | CTO·VPE·기술임원 (예산·결재 의사결정자) |
| 목표 행동 | 페이지 종료 후 **mailto: CTA 클릭** → 도입 문의 메일 발송 |
| 전환 신호 | 메일 도착 (별도 분석 도구 없이 측정) |
| 전달 맥락 | 메일·링크 자가 읽기 |

### 1-3. 메인 프레이밍

**핵심 명제**:

> **"AI가 언어·플랫폼 무관하게 소프트웨어 엔지니어링 수준을 적은 비용·짧은 기간에 끌어올리고, 개발자의 학습 속도까지 가속해 지속 개선을 가능하게 한다."**

두 축으로 분해해 페이지를 리드한다:

| 축 | 메시지 | 페이지 표현 |
|----|--------|------------|
| **Level Boost** | "스택 무관·저비용·단기간으로 SE 수준을 끌어올리고 지속 개선한다" | §1 Hero 메인 카피, §2 카드의 "현재의 마찰" + "AI Level Boost" 슬롯, §4 DORA 지표 |
| **Learning Acceleration** | "AI를 학습 도구로 활용해 개발자 역량을 빠르게 향상시킨다 — 워크숍 자체가 라이브 데모" | §2 카드의 "AI Level Boost" 슬롯 안 학습 가속 라인, §3 두 방법론의 학습 가속 효과, §3 하단 라이브 데모 카피 |

이전 안의 "Friction-led + Methodology-led"는 이 두 축에 흡수된다. **마찰 제거**는 Level Boost의 메커니즘, **자가 체득**은 Learning Acceleration의 메커니즘이다. CTO 언어(비용·기간·지속 개선)가 §1부터 진입하므로, 비개발자 트랙처럼 §5에서야 등장하는 비대칭을 해소한다.

### 1-4. 인터뷰 결정 사항

브레인스토밍 인터뷰(2026-05-26)에서 확정한 결정:

| # | 결정 항목 | 값 |
|---|----------|---|
| 1 | 1차 청중 | 엔지니어링 매니저·개발팀장 |
| 2 | 2차 청중 | CTO·VPE·기술임원 |
| 3 | 목표 행동 | mailto 도입 문의 |
| 4 | 전달 맥락 | 메일·링크 자가 읽기 |
| 5 | 메인 프레이밍 | Level Boost + Learning Acceleration (v2 재정의) |
| 6 | §2 쇼케이스 구조 | 5개 모범사례 카드, 4슬롯 + 헤더·푸터 시각 흐름 |
| 7 | §4 매트릭스 콘텐츠 | 모범사례 × DORA 지표 (점수 톤다운 적용) |
| 8 | §3 방법론 | 인터뷰 퍼스트 + Human-in-the-loop + 학습 가속 라인 |
| 9 | 시각 톤 | Linear/Vercel 미니멈·테크 (비개발자와 동일) |
| 10 | 브랜드 | ROBOCO 워크숍 제품 소개 (특정 고객사 비식별) |
| 11 | §5 스택 표현 | "적용 가능 스택" (검증 범위가 아닌 적용 범위로 표현) |

### 1-5. 정직성 원칙

- 5개 모범사례 카드의 미니 목업은 **터미널/코드/문서 캡처 콘셉트**다. 실제 SaaS UI가 아니므로 각 카드 하단에 **"💡 워크숍에서 만든 패턴의 결과 콘셉트입니다"** 캡션을 명시한다.
- "검증 이력" 컬럼은 비개발자 페이지와 동일하게 일반화된 표현(반복 운영·보안 검토·실증)을 사용한다. 구체 고객사명은 노출하지 않는다.
- "적용 가능 스택" 컬럼(§5)은 RealWorld 오픈소스 구현체가 존재하는 스택을 기준으로 한다. 모든 스택에서 워크숍이 동일 빈도로 운영된 적이 있다는 의미는 아니다.
- §2 "05 팀 확산 플레이북"은 모범사례라기보다 워크숍 마무리 활동의 산출물이다. 이름과 카피에서 활동임을 명확히 한다.

## 2. 파일 구조

### 2-1. 디렉토리

```
vibecoding-for-developer/portfolio/
├── index.html                 ← 메인 랜딩페이지 (단일 파일)
├── styles.css                 ← 공통 스타일 시스템 (비개발자와 동일 토큰 + 코드 영역 추가)
├── scripts.js                 ← 인터랙션 (IntersectionObserver)
├── assets/
│   ├── og-image.png           ← Open Graph 카드 (1200×630)
│   ├── favicon.svg            ← ROBOCO 마크
│   └── mockups/               ← 5개 SVG 목업
│       ├── 01-context.svg     ← 컨텍스트 엔지니어링 (CLAUDE.md)
│       ├── 02-spec.svg        ← 스펙 우선 개발 (OpenSpec)
│       ├── 03-test.svg        ← 자동화 테스트 + 린트 (Makefile/터미널)
│       ├── 04-gate.svg        ← 품질 게이트 (Git Hooks)
│       └── 05-playbook.svg    ← 팀 확산 플레이북 (튜토리얼 + migration-plan)
└── README.md                  ← 수정·배포 가이드
```

### 2-2. 아키텍처 원칙

- **빌드 단계 없음** — HTML/CSS/JS/SVG만 사용. 브라우저에서 `index.html` 더블 클릭으로 동작
- **단일 페이지** — 모든 콘텐츠 인라인, 외부 의존 0
- **시각 시스템 재사용** — `styles.css`는 비개발자 페이지의 토큰을 그대로 복사하고, §5-1의 코드/터미널 토큰만 추가. 초기 출시는 복사로 시작해 두 페이지 간 독립성 유지
- **GitHub Pages 자동 발행** — `_config.yml`의 발행 대상에 추가

### 2-3. 파일 산출 책임

| # | 파일 | 책임 | 분량 추정 |
|---|------|------|----------|
| 1 | `styles.css` | 비개발자 styles.css 복사 + 코드/터미널 토큰 (§5-1) 추가 | ~430줄 |
| 2 | `assets/mockups/01~05.svg` | 5개 SVG 목업 (코드/터미널/문서 캡처 스타일) | 각 ~150줄 |
| 3 | `index.html` | 6섹션 + 메타 + SVG 참조 | ~360줄 |
| 4 | `scripts.js` | IntersectionObserver 페이드 인 (비개발자와 동일) | ~30줄 |
| 5 | `assets/og-image.png` | Open Graph 카드 — Hero 카피 + ROBOCO 워드마크 | 1200×630 |
| 6 | `assets/favicon.svg` | ROBOCO 마크 (비개발자와 동일) | ~10줄 |
| 7 | `README.md` | 수정·배포 가이드 | ~50줄 |

작성 순서: 토큰 CSS 복사·확장 → SVG 목업 5종 → HTML 골격 → scripts.js → 메타 자산.

## 3. 콘텐츠 설계 — 6개 섹션

### § 1. Hero

**핵심 메시지**: "스택 무관·저비용·단기간 — AI로 SE 수준을 끌어올리고, 개발자 학습까지 가속"

**구성요소**

| 슬롯 | 내용 |
|------|------|
| Eyebrow | "개발자 바이브 코딩 워크숍" |
| H1 (display 56px) | **"AI가 소프트웨어 엔지니어링 수준을 적은 비용·짧은 기간에 끌어올립니다"** |
| 보조 카피 | "스택 무관 — Python·Go·TypeScript·React 무엇이든. 4시간 안에 자기 코드에서 직접 체득하고, AI를 학습 도구로 활용해 지속 개선하는 패턴까지 가져갑니다. Claude 기반 — 시니어 개발자 10~20명." |
| 1차 CTA (메일) | "도입 문의하기 →" |
| 2차 CTA (스크롤) | "모범사례 5종 보기 ↓" |
| 워드마크 | ROBOCO |

### § 2. 결과물 쇼케이스 (페이지의 시각적 중심)

**핵심 메시지**: "AI가 활성화하는 5개 영역의 SE 수준 향상 — 4시간 안에 자기 코드에 적용"

**레이아웃**: 5개 카드 종단 배치. 각 카드 약 80vh. 스크롤하며 1개씩 등장 (비개발자와 동일).

**카드 시각 흐름 (헤더 → 4슬롯 → 푸터)**

| 영역 | 내용 |
|------|------|
| **(헤더)** | 번호 `01 / 05` + 영역 이름 + 한 줄 정의 |
| **슬롯 1: 현재의 마찰** | 왜 비용·기간이 컸는가 — 설문 데이터 인용 |
| **슬롯 2: AI Level Boost** | AI가 수준을 끌어올리는 메커니즘 (Friction 제거) + **학습 가속 한 줄** (Learning Acceleration) |
| **슬롯 3: 산출물 + 지속 효과** | 워크숍 후 무엇이 남고, 어떻게 팀이 반복 적용하는가 |
| **(푸터)** | 미니 목업 SVG + 정직성 캡션 |

카드 한 장이 "마찰 → AI 활성화 → 산출물·지속" 3단계로 읽힌다. 세부 정보(자가 도입 방법·구현 디테일)는 슬롯 안 본문에 녹이되, 시각적으로는 3구간으로 분리.

**5개 영역 콘텐츠**

#### 01 / 05 — 컨텍스트 엔지니어링

| 영역 | 값 |
|------|---|
| 정의 | "AI가 프로젝트를 이해할 수 있도록 컨텍스트를 코드처럼 관리한다 (CLAUDE.md, /init)" |
| 슬롯 1 — 현재의 마찰 | "설문 60%가 'AI에게 코드베이스를 효과적으로 전달하지 못함'을 도입 1위 장애물로 꼽았다. 컨텍스트는 사람이 매번 채팅에 다시 붙여넣고, 신입은 코드를 읽어 추측한다." |
| 슬롯 2 — AI Level Boost | "**Friction 제거**: `/init`이 프로젝트 구조를 자동 스캔해 CLAUDE.md 초안 생성, 인터뷰 퍼스트 패턴이 빠진 맥락을 AI가 질문해 채운다. **학습 가속**: AI의 질문이 학생의 모호한 이해를 명시화 → '무엇을 모르는지' 자체를 알게 된다." |
| 슬롯 3 — 산출물 + 지속 효과 | "CLAUDE.md · 인터뷰 퍼스트 프롬프트 키트. 새 모듈·도메인 추가 시 동일 패턴 반복 → 컨텍스트가 코드와 함께 진화하고, 신입 온보딩 시간이 단축된다." |
| 미니 목업 콘셉트 | 좌측 프로젝트 트리, 우측 CLAUDE.md 미리보기 + Claude Code 인터뷰 대화 |

#### 02 / 05 — 스펙 우선 개발

| 영역 | 값 |
|------|---|
| 정의 | "변경 전에 OpenSpec으로 명세를 만들고, AI가 명세를 컨텍스트로 코드를 생성한다" |
| 슬롯 1 — 현재의 마찰 | "스펙은 항상 outdated. 작성 시간 부족, 결국 코드가 진실의 원천이 되고, 합류한 팀원은 코드를 읽어 추측한다." |
| 슬롯 2 — AI Level Boost | "**Friction 제거**: OpenSpec init이 기존 코드에서 스펙 역추출, `openspec propose`로 변경 제안을 생성. 같은 스펙이 테스트·문서·코드리뷰의 공통 컨텍스트가 된다. **학습 가속**: 시니어도 처음 보는 OpenSpec 도구를 AI 페어와 4시간 안에 실전 사용." |
| 슬롯 3 — 산출물 + 지속 효과 | "OpenSpec 스펙 디렉토리 · Claude 스킬(`.claude/skills/`). 스펙↔코드 드리프트를 AI가 자동 감지 → 문서 노후화 비용 자체가 사라진다." |
| 미니 목업 콘셉트 | `openspec/specs/` 트리 + 변경 제안 diff + Claude 스킬 호출 |

#### 03 / 05 — 자동화 테스트 + 코드 품질

| 영역 | 값 |
|------|---|
| 정의 | "AI가 사양 기반 테스트와 린트 설정을 작성, 사람이 검수, Makefile로 한 줄 실행" |
| 슬롯 1 — 현재의 마찰 | "설문 47%가 테스트를 최대 병목으로 답했다. 시간 부족으로 작성을 미루고, 작성된 테스트도 사양과 동기화 안 됨. 린트 설정 또한 프로젝트 초기에 잡고 끝나면 진화하지 않는다." |
| 슬롯 2 — AI Level Boost | "**Friction 제거**: OpenSpec 스펙을 컨텍스트로 → AI가 '사양 기반' 테스트 생성. Human-in-the-loop 검수가 환각 우려(87%)에 직접 대응. 린트 룰도 AI가 코드를 보고 적합한 셋업을 제안. **학습 가속**: 검토 과정에서 AI의 추론을 따라가며 학생이 테스트 설계 감각을 빠르게 체화." |
| 슬롯 3 — 산출물 + 지속 효과 | "단위 테스트 · E2E 테스트 · 린트 설정 · Makefile · 커버리지 ≥80%. 새 기능마다 동일 패턴 반복 → 팀 전원이 같은 출발선." |
| 미니 목업 콘셉트 | `make test` 실행 결과 터미널 (lint·unit·e2e 단계별 통과) + 커버리지 미니바 |

#### 04 / 05 — 품질 게이트

| 영역 | 값 |
|------|---|
| 정의 | "pre-commit / pre-push hook이 로컬에서 즉시 품질 검증을 강제한다" |
| 슬롯 1 — 현재의 마찰 | "설문 33%가 CI 자동화 검사가 거의 없다고 답했다. 검사가 PR 머지 후나 배포 직전에 처음 발견되고, 33% 팀은 PR 자동 품질 게이트도 활용하지 않는다." |
| 슬롯 2 — AI Level Boost | "**Friction 제거**: AI가 03에서 만든 린트·테스트를 hook 스크립트로 묶어준다. pre-commit이 커밋마다 린트+단위 테스트, pre-push가 푸시 시 E2E+커버리지. 복잡한 CI 파이프라인 없이 워크숍 직후 적용. **학습 가속**: hook 동작을 통과/차단 양방향으로 시연해 학생이 게이트의 의미를 실전 체득." |
| 슬롯 3 — 산출물 + 지속 효과 | "`.git/hooks/pre-commit` · `.git/hooks/pre-push` · 훅 공유 스크립트. 팀 전원이 동일한 훅 → 코드 품질이 사람에 의존하지 않고 프로세스에 의존." |
| 미니 목업 콘셉트 | `git commit` 시점에 hook이 차단(실패)하는 터미널 + 통과 시 ✓ 흐름 |

#### 05 / 05 — 팀 확산 플레이북

| 영역 | 값 |

### § 3. Methodology — 두 방법론 (학습 가속 포함)

**핵심 메시지**: "AI를 믿을 수 있게 만드는 두 패턴 — 컨텍스트 부족과 환각 우려를 구조적으로 해결하면서, 동시에 개발자 학습을 가속한다"

**레이아웃**: 2단 분할 (비개발자와 동일 구조)

| 좌 | 우 |
|---|---|
| **인터뷰 퍼스트 패턴** | **Human-in-the-loop 검증** |
| "해줘"가 아닌 "나에게 질문해줘" | AI 생성 → 사람 검토 → 실행 → 피드백 |
| ↓ 컨텍스트 부족(60%) 구조적 해결 | ↓ 환각 우려(87%) 직접 대응 |
| 🎓 **학습 가속**: AI의 질문이 학생의 모호한 이해를 명시화 → "무엇을 모르는지 알게 됨" | 🎓 **학습 가속**: 검토 과정에서 AI의 추론을 학습 → 다음에는 더 빠르게 판단 |

**보조 카피**: "87%의 개발자가 'AI 환각'을 우려한다. 답은 '더 똑똑한 AI'가 아니라 '환각을 잡아내는 프로세스'다 — 그리고 그 프로세스는 학습도 가속한다."

**Footnote** (라이브 데모 명시):

> "이 두 패턴은 워크숍에서 단순히 설명되는 게 아니라 시연됩니다. 시니어 개발자가 처음 보는 OpenSpec·Claude Skill·Git Hooks를 AI와 함께 4시간 안에 자기 코드에 적용 — **워크숍 자체가 라이브 데모입니다.**"

**비개발자 트랙과의 짝**: 비개발자 §3은 "인터뷰 퍼스트 + 검수 루프(자가 비판)". 개발자 §3은 "인터뷰 퍼스트 + Human-in-the-loop"로 산업 표준 용어를 사용하고, 학습 가속 라인을 추가.

### § 4. Matrix — 모범사례 × DORA 지표

**핵심 메시지**: "자가 도입 팀이 무엇을 측정할 수 있게 되는가 — 5개 영역이 4개 DORA 지표에 어떻게 작용하는가"

**레이아웃**: 5행(영역) × 4열(DORA 지표) 그리드. 각 셀에 점수 기호 + 텍스트 라벨(색상 비의존 인코딩).

| | 배포 빈도 | 변경 리드타임 | 변경 실패율 | MTTR |
|---|---|---|---|---|
| 01 컨텍스트 엔지니어링 | ◯ Side | ◐ Indirect *(온보딩·분석 단축)* | ◐ Indirect | ◐ Indirect |
| 02 스펙 우선 개발 | ◯ Side | ● Direct | ● Direct | ◐ Indirect |
| 03 자동화 테스트 + 코드 품질 | ◐ Indirect *(안정성→빈도 가능)* | ◐ Indirect | ● Direct | ◯ Side |
| 04 품질 게이트 | ◐ Indirect *(차단·통과 분리)* | ◐ Indirect | ● Direct | ◐ Indirect |
| 05 팀 확산 플레이북 | ◐ Indirect | ◐ Indirect | ◐ Indirect | ◯ Side |

**범례**: ● Direct (직접) · ◐ Indirect (간접) · ◯ Side (부수)

이 점수는 *기대 작용 방향*이며, 실제 효과 크기는 팀의 베이스라인에 따라 달라진다. 직접/간접의 구분은 효과의 인과 거리(메커니즘이 몇 단계인가)를 의미한다.

**보조 카피**: "DORA 4지표는 'AI 도입 효과'를 정량화하는 보편적 언어다. 워크숍은 측정 도구를 제공하지 않지만, 5개 영역이 각 지표에 어떻게 작용하는지를 명확히 한다. 측정 기반 구축이 필요한 팀에는 도입 후 후속 컨설팅으로 별도 지원한다."

**왜 DORA인가**: CTO·매니저 모두가 이해할 수 있는 보편적 측정 언어. "이 워크숍이 어떤 지표를 움직이는가"를 한 장에 답한다.

## 5. 시각 디자인 시스템

비개발자 페이지의 토큰 시스템(`2026-05-19-portfolio-slides-design.md` §5)을 **그대로 재사용**한다. 컬러·타이포·간격·컴포넌트·모션 토큰은 모두 동일하다. 다음을 개발자 페이지 전용으로 추가한다.

### 5-1. 추가 토큰 — 코드/터미널 영역

```css
:root {
  --code-bg: #0D0D10;          /* 라이트 모드의 코드 배경(다크 박스) */
  --code-text: #E4E4E7;
  --code-prompt: #7FB069;      /* 초록 프롬프트 */
  --code-output-dim: rgba(228, 228, 231, 0.7);
  --code-success: #4ADE80;
  --code-error: #F87171;
  --code-border: #2D2D35;      /* 다크 박스 외곽 */
}

@media (prefers-color-scheme: dark) {
  :root {
    --code-bg: #050507;
    --code-text: #FAFAFA;
    --code-border: #1F1F25;
  }
}

.code-block {
  font-family: "SF Mono", Menlo, "Cascadia Code", Consolas, monospace;
  font-size: 13px;
  line-height: 1.6;
  background: var(--code-bg);
  color: var(--code-text);
  padding: var(--space-4);
  border-radius: var(--radius);
  border: 1px solid var(--code-border);
}
```

**대비 기준 (WCAG)**:

| 페어 | 라이트 모드 | 다크 모드 | 기준 |
|------|------------|----------|------|
| `--code-text` vs `--code-bg` | #E4E4E7 vs #0D0D10 ≈ 14:1 | #FAFAFA vs #050507 ≈ 18:1 | AAA 본문 7:1 충족 |
| `--code-success` vs `--code-bg` | #4ADE80 vs #0D0D10 ≈ 9:1 | 동일 | AA Large 충족 |
| `--code-error` vs `--code-bg` | #F87171 vs #0D0D10 ≈ 6:1 | 동일 | AA 본문 4.5:1 충족 |
| `--code-border` vs `--bg` | #2D2D35 vs #FFFFFF ≈ 12:1 | #1F1F25 vs #0A0A0A ≈ 1.7:1 | 비텍스트 3:1 (다크 모드는 그림자 추가로 보완) |

다크 모드에서 `--code-border` 대비가 낮으면 박스 분리감이 약해진다. `box-shadow: 0 0 0 1px rgba(255,255,255,0.06) inset` 또는 `outline: 1px solid var(--border)`로 보완.

### 5-3. 색상 비의존 인코딩 원칙

- §4 DORA 매트릭스의 ●/◐/◯ 점수는 셀 안에 텍스트(Direct/Indirect/Side)를 병기한다.
- 통과/실패 상태(03·04 목업)는 색 + 기호(✓/✗) + 텍스트("OK"/"FAIL") 세 가지 신호를 동시 사용.
- 커버리지 바(03 목업)는 색뿐 아니라 백분율 텍스트를 함께 표시.

### 5-4. 모션·인터랙션

비개발자와 동일 — `.section-fade-in` IntersectionObserver 페이드 인. `prefers-reduced-motion` 존중.

## 10. 변경 이력

### v2 — 2026-05-26 (Codex 리뷰 + 사용자 새 프레이밍 반영)

- **메인 프레이밍 격상**: "Friction-led + Methodology-led" → "Level Boost + Learning Acceleration". CTO 언어(비용·기간·지속 개선)가 §1부터 진입.
- **§1 Hero 카피 재작성**: 스택 무관·저비용·단기간·학습 가속을 명시.
- **§2 5번 카드 개명**: "모범사례 전파" → "팀 확산 플레이북" (활동임을 정직하게 표시).
- **§2 03 카드 확장**: "자동화 테스트" → "자동화 테스트 + 코드 품질" (린트를 명시적 산출물로 격상).
- **§2 카드 슬롯 4개로 정리**: 헤더 + (마찰 / AI Level Boost / 산출물+지속 효과) + 푸터의 시각 흐름. 자가 도입 방법은 슬롯 3에 흡수.
- **§3 학습 가속 라인 추가**: 두 패턴 각각에 학습 가속 효과 한 줄 + 하단에 "워크숍 자체가 라이브 데모" Footnote.
- **§4 DORA 점수 톤다운**: 과장된 ●을 ◐으로 조정 ("컨텍스트 → 리드타임 ●" 등). 각 셀에 텍스트 라벨(Direct/Indirect/Side) 병기 — 색상 비의존 인코딩.
- **§4 보조 카피 재작성**: "베이스라인 30분 세션" 삭제(PRD 시간표에 없음), "자가 도입 팀이 무엇을 측정하는가"로 연결, 후속 컨설팅 가능성 명시.
- **§5 "다중 스택 실증" → "적용 가능 스택"**: RealWorld 구현체 기준의 안전한 표현으로 확정.
- **§5-1 코드/터미널 대비 기준 명시**: WCAG 등급별 대비비 표 추가, 다크 모드 외곽 보완 방법 명시.
- **§5-3 색상 비의존 인코딩 원칙 추가**: §4 매트릭스, 03·04 목업 통과/실패에 모두 적용.
- **§4-1 목업 본문 임계선**: 카드 안 축소 표시 시 가독성 확보를 위해 최상위 본문 22px+ 명시.
