# Design Spec: 개발자 바이브 코딩 워크숍 포트폴리오 랜딩페이지

> 작성일: 2026-05-26 | 작성자: ROBOCO | 상태: 디자인 확정, 구현 대기

## 1. 개요

### 1-1. 목적

개발자 바이브 코딩 워크숍을 외부 고객(엔지니어링 매니저·CTO)에게 소개하고 **도입 문의를 유도**하는 HTML 포트폴리오 랜딩페이지를 제작한다. 비개발자 트랙 페이지([roboco.io/vibecoding-workshop/.../vibecoding-for-nondeveloper/portfolio/](https://roboco.io/vibecoding-workshop/vibecoding-for-nondeveloper/portfolio/))와 동일한 시각 시스템·구조를 공유하되, 콘텐츠와 메인 프레이밍은 개발자 트랙의 가치 명제에 맞춰 새로 설계한다.

### 1-2. 청중과 목표 행동

| 항목 | 정의 |
|------|------|
| 1차 청중 | 엔지니어링 매니저·개발팀장 (팀 도입 결정자) |
| 2차 청중 | CTO·VPE·기술임원 (예산·결재 의사결정자) |
| 목표 행동 | 페이지 종료 후 **mailto: CTA 클릭** → 도입 문의 메일 발송 |
| 전환 신호 | 메일 도착 (별도 분석 도구 없이 측정) |
| 전달 맥락 | 메일·링크 자가 읽기 |

### 1-3. 메인 프레이밍

**핵심 명제**: "AI를 활용해서 모던 소프트웨어 엔지니어링의 모범사례를 손쉽게 도입하는 방법을 스스로 터득한다."

이 명제를 두 축으로 분해해 페이지를 리드한다:

| 축 | 메시지 | 페이지 표현 |
|----|--------|------------|
| **Friction-led** | "모범사례 도입의 마찰을 AI가 제거한다" | §1 Hero 메인 카피, §2 카드의 "현재의 마찰" 슬롯 |
| **Methodology-led** | "도구가 아닌 자가 도입 방법론을 체득한다" | §2 카드의 "자가 도입 방법" 슬롯, §3 두 방법론 |

비개발자 트랙은 "5개 독립 도구를 만든다(DELIVERABLES-led)"가 메인이었던 반면, 개발자 트랙은 **방법론 자가 체득**이 메인이다. 이 차이가 §2 카드의 의미를 "도구 5종"에서 "AI로 활성화되는 모범사례 5종"으로 바꾼다.

### 1-4. 인터뷰 결정 사항

브레인스토밍 인터뷰(2026-05-26)에서 확정한 결정:

| # | 결정 항목 | 값 |
|---|----------|---|
| 1 | 1차 청중 | 엔지니어링 매니저·개발팀장 |
| 2 | 2차 청중 | CTO·VPE·기술임원 |
| 3 | 목표 행동 | mailto 도입 문의 |
| 4 | 전달 맥락 | 메일·링크 자가 읽기 |
| 5 | 메인 프레이밍 | Friction-led + Methodology-led 조합 |
| 6 | §2 쇼케이스 구조 | 5개 모범사례 카드 (비개발자와 카드 수 동일, 의미 재정의) |
| 7 | §4 매트릭스 콘텐츠 | 모범사례 × DORA 지표 |
| 8 | §3 방법론 | 인터뷰 퍼스트 + Human-in-the-loop (6-pager 명시) |
| 9 | 시각 톤 | Linear/Vercel 미니멈·테크 (비개발자와 동일) |
| 10 | 브랜드 | ROBOCO 워크숍 제품 소개 (특정 고객사 비식별) |

### 1-5. 정직성 원칙

- 5개 모범사례 카드의 미니 목업은 **터미널/코드/문서 캡처 콘셉트**다. 실제 SaaS UI가 아니므로 각 카드 하단에 **"💡 워크숍에서 만든 패턴의 결과 콘셉트입니다"** 캡션을 명시한다.
- "검증 이력" 컬럼은 비개발자 페이지와 동일하게 일반화된 표현(반복 운영·보안 검토·실증)을 사용한다. 구체 고객사명은 노출하지 않는다.

## 2. 파일 구조

### 2-1. 디렉토리

```
vibecoding-for-developer/portfolio/
├── index.html                 ← 메인 랜딩페이지 (단일 파일)
├── styles.css                 ← 공통 스타일 시스템 (비개발자와 동일 토큰)
├── scripts.js                 ← 인터랙션 (IntersectionObserver)
├── assets/
│   ├── og-image.png           ← Open Graph 카드 (1200×630)
│   ├── favicon.svg            ← ROBOCO 마크
│   └── mockups/               ← 5개 SVG 목업
│       ├── 01-context.svg     ← 컨텍스트 엔지니어링 (CLAUDE.md)
│       ├── 02-spec.svg        ← 스펙 우선 개발 (OpenSpec)
│       ├── 03-test.svg        ← 자동화 테스트 (Makefile/터미널)
│       ├── 04-gate.svg        ← 품질 게이트 (Git Hooks)
│       └── 05-spread.svg      ← 모범사례 전파 (migration-plan)
└── README.md                  ← 수정·배포 가이드
```

### 2-2. 아키텍처 원칙

- **빌드 단계 없음** — HTML/CSS/JS/SVG만 사용. 브라우저에서 `index.html` 더블 클릭으로 동작
- **단일 페이지** — 모든 콘텐츠 인라인, 외부 의존 0
- **시각 시스템 재사용** — `styles.css`는 비개발자 페이지의 토큰을 그대로 복사. 색·타이포·간격·컴포넌트가 통일된다. (장기적으로 공통 추출 가능하나, 초기 출시는 복사로 시작해 두 페이지 간 독립성 유지)
- **GitHub Pages 자동 발행** — `_config.yml`의 발행 대상에 추가

### 2-3. 파일 산출 책임

| # | 파일 | 책임 | 분량 추정 |
|---|------|------|----------|
| 1 | `styles.css` | 디자인 토큰 시스템 (비개발자 styles.css 복사 + 개발자 트랙 전용 클래스 추가) | ~400줄 |
| 2 | `assets/mockups/01~05.svg` | 5개 SVG 목업 (코드/터미널/문서 캡처 스타일) | 각 ~150줄 |
| 3 | `index.html` | 6섹션 + 메타 + SVG 참조 | ~360줄 |
| 4 | `scripts.js` | IntersectionObserver 페이드 인 (비개발자와 동일) | ~30줄 |
| 5 | `assets/og-image.png` | Open Graph 카드 — Hero 문구 + ROBOCO 워드마크, 다크 배경 + 인디고 액센트 | 1200×630 |
| 6 | `assets/favicon.svg` | ROBOCO 마크 (비개발자와 동일) | ~10줄 |
| 7 | `README.md` | 수정·배포 가이드 | ~50줄 |

작성 순서: 토큰 CSS 복사 → SVG 목업 5종 → HTML 골격 → scripts.js → 메타 자산.

### § 3. Methodology — 두 방법론

**핵심 메시지**: "AI를 믿을 수 있게 만드는 두 패턴 — 컨텍스트 부족과 환각 우려를 구조적으로 해결한다"

**레이아웃**: 2단 분할 (비개발자와 동일 구조)

| 좌 | 우 |
|---|---|
| **인터뷰 퍼스트 패턴** | **Human-in-the-loop 검증** |
| "해줘"가 아닌 "나에게 질문해줘" | AI 생성 → 사람 검토 → 실행 → 피드백 |
| ↓ 컨텍스트 부족(60%) 구조적 해결 | ↓ 환각 우려(87%) 직접 대응 |

**보조 카피**: "87%의 개발자가 'AI 환각'을 우려한다. 답은 '더 똑똑한 AI'가 아니라 '환각을 잡아내는 프로세스'다."

**비개발자 트랙과의 짝**: 비개발자 §3은 "인터뷰 퍼스트 + 검수 루프(자가 비판)". 개발자 §3은 "인터뷰 퍼스트 + Human-in-the-loop"로 산업 표준 용어를 사용한다.

### § 4. Matrix — 모범사례 × DORA 지표

**핵심 메시지**: "5개 모범사례가 4개 DORA 지표를 어떻게 개선하는가 — 측정 가능한 효과"

**레이아웃**: 5행(모범사례) × 4열(DORA 지표) 그리드

| | 배포 빈도 | 변경 리드타임 | 변경 실패율 | MTTR |
|---|---|---|---|---|
| 01 컨텍스트 엔지니어링 | ◐ | ● | ◐ | ◐ |

**범례**: ● 직접 영향 · ◐ 간접 영향 · ◯ 부수 효과

**보조 카피**: "설문 87%가 DORA 지표를 측정하지 않는다. 워크숍은 베이스라인 설정 30분 세션을 포함해, 4주 후 효과를 숫자로 확인할 수 있게 한다."

### 4-2. 목업 01 — 컨텍스트 엔지니어링

**레이아웃**: 좌측 프로젝트 트리 (1/3) + 우측 CLAUDE.md + 인터뷰 대화 (2/3)

**레이아웃**: 좌측 스펙 트리 (1/3) + 중앙 변경 제안 diff (1/3) + 우측 Claude 스킬 (1/3)

**레이아웃**: 상단 Makefile 미리보기 (1/3) + 중앙 터미널 실행 (1/2) + 하단 커버리지 미니바 (1/6)

  - `▶ lint` → `✓ 0 warnings`

**우측 상단 (실패 시나리오)**

**우측 하단 (통과 시나리오)**
