# 개발자를 위한 바이브 코딩 워크숍

**시니어 개발자 대상 | 10~20명 | 4시간**

---

## 1. 서론: 우리는 이미 AI를 쓰고 있다. 문제는 '어떻게'다.

시니어 개발자 대상 사전 설문을 실시하면, 거의 예외 없이 동일한 패턴이 나타난다. 대다수가 Claude나 Copilot 같은 AI 코딩 도구를 이미 사용 중이고, 상당수가 팀 단위로 AI 사용 정책까지 운영하고 있다. 코드 생성, 설계, 코드 리뷰 보조, 디버깅 — 수치만 보면 AI 도입이 완료된 조직처럼 보인다.

그러나 같은 설문의 다른 항목은 다른 그림을 보여준다. CI 자동화 검사가 거의 없는 팀이 30%대이고, 완전 자동 배포를 갖춘 팀은 15% 미만인 경우가 대부분이다. AI 결과물의 환각 문제를 우려하는 비율은 80%를 넘는다.

이것이 이 워크숍이 해결해야 할 핵심 격차다. **AI 도구를 쓰는 것**과 **AI를 개발 파이프라인에 안전하게 통합하는 것** 사이의 간극. 개발자들은 AI로 코드를 생성하고 있지만, 그 코드가 신뢰할 수 있는지 검증하는 체계가 없다. 테스트가 최대 병목이고, 컨텍스트 부족이 AI 도입의 최대 장애물이라는 설문 결과는 이 간극을 정량적으로 보여준다.

이 워크숍은 "AI를 더 잘 쓰는 법"을 가르치지 않는다. **AI가 생성한 코드를 신뢰할 수 있게 만드는 파이프라인을 구축하는 법**을 가르친다.

---

## 2. 참가자: 기초가 필요 없는, 실전이 필요한 사람들

이 워크숍의 대상은 AI 코딩 도구를 이미 사용 중인 3년 이상 경력의 시니어 개발자다. 프론트엔드, 백엔드, ML/AI, 풀스택, DevOps 등 역할이 다양하고, Python, Go, TypeScript, React 등 주력 스택도 제각각이다.

이 프로파일에서 도출한 설계 원칙은 명확하다.

첫째, **기초 설명을 하지 않는다.** AI가 무엇인지, Claude Code가 어떻게 동작하는지 설명하는 시간은 0분이다. 참가자 전원이 이미 매일 쓰고 있다.

둘째, **범용 패턴 중심으로 설계한다.** 다양한 스택이 혼재하는 환경에서 특정 스택에 종속된 실습은 상당수의 참가자를 소외시킨다. 대신 어떤 스택에서든 적용 가능한 프롬프트 패턴과 프로세스를 다룬다.

셋째, **실무 코드 대신 오픈소스를 쓴다.** 기업 환경의 개발자 중 상당수가 코드 외부 반출이 불가능한 보안 제약을 받고 있다. RealWorld 오픈소스 프로젝트를 실습 대상으로 선택함으로써 보안 문제를 원천 차단하면서도, 실제 애플리케이션 수준의 복잡도를 유지한다.

---

## 3. 워크숍 구조: 문서화 → 테스트 → CI/CD의 3단계 파이프라인

4시간을 세 개의 실습 단계와 마무리로 구성한다. 강사 발표는 오프닝 20분이 전부이고, 나머지 3시간 40분은 전부 실습이다.

### 오프닝 & 환경 확인 (20분)

바이브 코딩의 현주소를 간략히 소개하고, 워크숍의 3단계 구조와 흐름을 설명한다. 환경 확인은 Claude Code YOLO 모드, OMC, OpenSpec, GitHub CLI 설치 상태를 점검하는 것으로 끝낸다. 10분 안에 해결되지 않는 환경 문제는 TA와 페어링으로 넘긴다. 환경 세팅에 시간을 낭비하는 것은 이 워크숍의 Non-Negotiable이다.

### 1단계: 문서화 (80분)

AI 협업의 품질은 컨텍스트의 품질에 의해 결정된다. 어떤 조직의 설문에서든 컨텍스트 부족이 AI 도입 장애물 상위에 오르는 것은 우연이 아니다. AI가 프로젝트를 제대로 이해하지 못하면, 생성하는 코드도 프로젝트와 동떨어진다.

이 단계에서는 참가자가 자기 스택에 맞는 RealWorld 구현체를 Fork한 뒤, 세 가지 문서화 작업을 수행한다. `/init`으로 CLAUDE.md를 생성하여 AI의 프로젝트 이해 기반을 구축한다. OpenSpec으로 프로젝트의 기능 스펙을 체계적으로 문서화한다. 그리고 이 문서들을 Claude 스킬로 전환하여, AI가 문서를 단순히 "읽는" 수준을 넘어 "활용하는" 수준으로 끌어올린다.

모든 과정에서 **인터뷰 퍼스트 패턴**을 적용한다. AI에게 "해줘"가 아니라 "나에게 질문해줘"로 시작한다. AI가 질문을 통해 프로젝트 맥락을 파악하고, 내 답변이 분석 범위를 한정하며, 정확한 정보 전달로 환각 가능성을 줄인다. 이 패턴 하나가 "AI가 이해할 수 있는 컨텍스트 부족"이라는 장애물에 대한 직접적인 해결책이다.

### 2단계: 테스트 구현 (70분)

개발 조직의 사전 설문에서 테스트는 거의 항상 최대 병목으로 나타나고, 테스트 코드 생성은 가장 원하는 AI 자동화 시나리오로 꼽힌다. 이 단계는 그 수요에 직접 대응한다.

1단계에서 생성한 OpenSpec 스펙을 기반으로 단위 테스트와 E2E 테스트를 작성한다. 스펙이 테스트의 근거가 되므로, AI가 "있을 법한" 테스트가 아니라 "사양에 기반한" 테스트를 생성한다. 린트를 설정하고, Makefile로 테스트·린트 명령어를 통합하여 단일 명령어로 전체 품질 검사를 실행할 수 있게 만든다.

여기서 핵심은 **Human-in-the-loop 검증 패턴**이다. AI가 테스트를 작성하면 사람이 검토하고, 승인 후 실행하고, 결과를 확인하고, 필요시 수정을 요청한다. 대다수가 우려하는 AI 환각 문제에 대한 해답은 "환각이 없는 AI"가 아니라 "환각을 잡아내는 프로세스"다.

### 3단계: CI/CD 구축 (50분)

CI 자동화 검사가 없거나, PR 머지 시 자동화된 품질 게이트를 활용하지 않는 팀이 의외로 많다. 이 단계에서는 Git Hooks로 로컬 품질 게이트를 구축한다.

pre-commit hook이 커밋할 때마다 린트 체크와 단위 테스트를 자동 실행하고, pre-push hook이 푸시할 때 E2E 테스트와 커버리지 체크(80% 이상)를 실행한다. 복잡한 CI/CD 파이프라인이 아니라, 개발자 로컬 환경에서 즉시 동작하는 품질 게이트다. 워크숍 끝나고 팀에 돌아가서 바로 적용할 수 있다.

## 4. 핵심 방법론: 인터뷰 퍼스트와 Human-in-the-loop

이 워크숍을 관통하는 두 가지 방법론이 있다.

**인터뷰 퍼스트 패턴**은 AI에게 작업을 지시하기 전에 "나에게 질문해줘"로 시작하는 방식이다. 전통적인 프롬프트 엔지니어링이 "어떻게 더 잘 지시할까"에 집중한다면, 인터뷰 퍼스트는 "AI가 무엇을 알아야 하는가"에 집중한다. AI가 질문을 통해 맥락을 파악하면, 결과물의 품질이 프롬프트 기교에 의존하지 않고 정보의 정확성에 의존하게 된다. 이것이 컨텍스트 부족 문제의 구조적 해결이다.

**Human-in-the-loop 검증 패턴**은 AI 출력을 맹신하지 않고, 검토 단계를 프로세스에 내장하는 방식이다. AI가 생성한 코드는 반드시 사람이 검토한 뒤 실행하고, 결과를 확인한 후 피드백을 반영한다. 환각 우려를 해결하는 방법은 AI를 더 똑똑하게 만드는 것이 아니라, 검증을 자동화하는 것이다. 테스트와 린트가 그 자동화된 검증이고, Git Hooks가 그 검증을 강제하는 게이트다.

이 두 방법론은 각각 AI 도입의 가장 흔한 장애물(컨텍스트 부족)과 가장 큰 우려(환각)에 대응한다. 워크숍의 3단계 구조는 이 방법론을 체화하는 실습 경로다. 문서화가 인터뷰 퍼스트로 컨텍스트를 구축하고, 테스트가 Human-in-the-loop로 검증을 자동화하며, CI/CD가 그 검증을 개발 워크플로우에 영구적으로 내장한다.

## 5. 산출물과 실무 전환

워크숍을 마치면 참가자는 8개의 산출물을 가지고 팀으로 돌아간다.

1단계에서 CLAUDE.md, OpenSpec 스펙 문서, Claude 스킬이 생성된다. 2단계에서 단위 테스트, E2E 테스트, 린트 설정, Makefile이 생성된다. 3단계에서 pre-commit hook과 pre-push hook이 구축된다. 마무리에서 튜토리얼 문서와 전환 계획서(migration-plan.md)가 완성된다.

특히 마무리 단계의 두 산출물은 실무 전환의 다리 역할을 한다. 튜토리얼은 Claude Code의 세션 로그를 분석하여 오늘 워크숍 전체 과정을 재현 가능한 문서로 만든 것이다. 전환 계획서는 generate-plan 스킬을 사용하여 자동 생성하되, 3~5라운드의 심층 인터뷰를 통해 각 참가자의 실무 환경에 맞춤화된다. 코드베이스 스캔 → 인터뷰 → 분석 요약 → 계획서 생성의 4단계 과정을 거치며, 인터뷰 응답의 품질이 계획서의 품질을 결정한다.

산출물은 RealWorld 오픈소스 프로젝트 위에 만들어지지만, 방법론은 어떤 프로젝트에든 적용 가능하다. `/init`으로 CLAUDE.md를 만들고, OpenSpec으로 스펙을 문서화하고, 인터뷰 퍼스트로 테스트를 작성하고, Git Hooks로 품질 게이트를 설치하는 것 — 이 과정은 스택에 무관하다.

## 6. 성공 기준과 리스크 관리

### 성공 기준

| 기준 | 목표 |
|------|------|
| 3단계 실습 완수 (문서화 → 테스트 → CI/CD) | 참가자 80% 이상 |
| 핵심 스킬 3개 이상 체험 (인터뷰 퍼스트, Human-in-the-loop, 스킬 생성) | 참가자 100% |
| AI 협업 프로세스 체화 | 참가자 100% |
| 전환 계획서(migration-plan.md) 완성 | 참가자 80% 이상 |
| 사후 만족도 | 80% 이상 |

"완주보다 깊이"가 이 워크숍의 원칙이다. 3단계를 다 끝내지 못해도, 현재 단계의 방법론을 체화하는 것이 피상적으로 모든 단계를 훑는 것보다 낫다.

### 리스크와 대응

**환경 세팅 지연**: 사전 준비로 Claude Code, OMC, OpenSpec, GitHub CLI 설치를 워크숍 1주 전에 완료하도록 안내한다. 보안팀 승인이 필요한 참가자에게는 설치 목록을 2주 전에 공유한다. 당일 10분 내 해결 안 되면 TA 페어링으로 전환한다.

**스택 다양성으로 인한 진도 차이**: RealWorld 프로젝트가 동일한 API 스펙의 다양한 구현체를 제공하므로, 각자 자기 스택을 사용하면서도 동일한 실습 구조를 따를 수 있다. 프롬프트는 스택 중립적으로 설계하되, TA를 스택별로 사전 배정하여 구현체 특화 문제에 대응한다.

**보안 제약**: 코드 외부 반출 불가, 승인된 SaaS만 허용 같은 제약은 RealWorld 오픈소스 사용과 Claude Code 로컬 CLI로 해결한다. 실무 코드를 건드리지 않으면서 실무에 적용 가능한 방법론을 익히는 것이 이 워크숍의 보안 전략이다.

---

**한 줄 요약**: AI를 쓰고 있지만 믿을 수 없는 시니어 개발자에게, AI가 생성한 코드를 신뢰할 수 있게 만드는 파이프라인(문서화 → 테스트 → CI/CD)을 4시간 안에 직접 구축하게 한다.
