# PRD: QA Plan·테스트 케이스·이슈 정리 자동화

> 비개발자 바이브 코딩 프로젝트 #5 | QA·운영(개발 경력) 직군 대상 | Claude Project + 인터뷰 퍼스트 패턴

## 1. 배경

비개발자 설문 12명 중 '기타' 응답자 2명 중 1명이 **QA 직군**, 다른 1명이 **개발 경력이 있는 운영 담당자**다. 설문 자유 응답에서 이 그룹이 직접 제출한 반복 업무:

- "테스트 케이스·QA Plan 작성"
- "백로그 이슈 정리"
- "버그 리포트 작성"
- "개발자 답변 신뢰도 확인"

QA·운영 직군은 **기능 명세를 받아 테스트 케이스로 펼치는 작업**과 **사용자·내부 보고된 raw 이슈를 재현 가능한 형태로 정리하는 작업**이 핵심 병목이다. 두 작업 모두 본질적으로 패턴화 가능하지만, 매 기능·매 이슈마다 처음부터 사람이 작성하고 있다.

QA 산출물은 정확성이 곧 품질이므로 **누락된 시나리오가 운영 사고로 직결**된다. AI는 정상 케이스만 제안하기 쉽기 때문에, 경계값·예외·회귀 시나리오까지 강제로 도출하는 프롬프트 설계가 필요하다.

## 2. 목표

### 핵심 목표

기능 명세를 입력하면 **QA Plan + 테스트 케이스(정상·경계·예외) + 회귀 후보**가, 이슈 raw 텍스트를 입력하면 **재현 단계 + 우선순위 + 분류**가 자동 생성되는 워크플로우를 구축한다.

### 성공 기준

| 기준 | 목표 |
|------|------|
| 기능 1건당 테스트 케이스 작성 시간 | 평균 3시간 → 1시간 (66% 단축) |
| 경계값·예외 시나리오 자동 도출 | 정상 케이스 대비 최소 2배 |
| 이슈 1건당 정리 시간 | 평균 20분 → 5분 (75% 단축) |
| 회귀 후보 자동 추출 정확도 | 검토자 채택률 70%+ |

### Non-Negotiable

- AI 생성 테스트 케이스는 **반드시 QA 담당자 검토 후 실행**
- 보안·결제 등 **고위험 기능은 사람 직접 작성 우선** (AI는 보조 역할만)

## 3. 사용자

| 항목 | 내용 |
|------|------|
| 주 사용자 | QA 담당자, 운영(개발 경력) |
| 보조 사용자 | PM·기획 (테스트 범위 협의 시) |
| 사용 빈도 | 매주 (스프린트 단위) |
| 사용 환경 | 회사 노트북 + 브라우저 |

## 4. 핵심 기능

### 4-1. 기능 명세 → QA Plan

- 기능 명세서·PRD 입력 → QA Plan 자동 작성
- 출력 섹션: **테스트 범위 / 위험 영역 / 우선순위 / 환경 / 일정 / 종료 기준**

### 4-2. 테스트 케이스 자동 펼치기

각 기능별로 강제 생성:
- **정상 케이스**: 기본 시나리오
- **경계값**: 최소·최대·0·NULL·공백
- **예외**: 잘못된 입력·권한 없음·네트워크 실패·동시성
- **회귀**: 영향 가능한 기존 기능 자동 식별

테스트 케이스 형식: ID / 사전 조건 / 단계 / 기대 결과 / 우선순위

### 4-3. 위험 영역 자동 식별

- 명세에서 **숨겨진 위험 요소** 자동 추출:
  - 외부 시스템 의존
  - 동시성 / 트랜잭션
  - 상태 변경 / 권한
  - 데이터 마이그레이션
  - 보안 / 결제

### 4-4. 이슈 raw 텍스트 → 구조화된 이슈 카드

사용자 신고·내부 메모를 입력하면 자동 생성:
- **재현 단계**: 1, 2, 3...
- **사전 조건**: 환경·계정·데이터
- **기대 결과 vs 실제 결과**
- **우선순위·심각도**: 영향 범위 기반
- **유형 분류**: 버그 / 사양 / 사용성 / 데이터 이슈
- **재현 가능 여부**: 명확/불명확/재현불가

### 4-5. 백로그 정리·우선순위 자동 산정

- 이슈 묶음 텍스트 입력 → 중복 제거 + 우선순위 정렬
- 유사 이슈 자동 그룹화

### 4-6. 회귀 테스트 후보 추출

- 변경된 기능과 과거 이슈 이력 비교
- 동일 영역·동일 모듈 과거 이슈에서 회귀 후보 자동 제안

## 5. 워크플로우

```
[1회 셋업]
  회사 QA 표준·테스트 케이스 양식 정의
       ↓
  Claude Project 생성 + 시스템 프롬프트 (위험 영역 체크리스트 포함)

[기능 단위 QA]
  기능 명세 입력
       ↓
  QA Plan 자동 생성 (인터뷰 퍼스트로 누락 정보 보완)
       ↓
  테스트 케이스 자동 펼치기 (정상/경계/예외/회귀)
       ↓
  QA 담당자 검토·보강
       ↓
  실행 → 결과 기록

[이슈 정리]
  raw 텍스트(사용자 신고·메모) 입력
       ↓
  구조화된 이슈 카드 자동 생성
       ↓
  중복·유사 묶음 그룹화
       ↓
  우선순위 정렬

[회귀 분석]
  변경 기능 + 과거 이슈 이력 입력
       ↓
  회귀 후보 자동 추출
       ↓
  회귀 테스트 케이스 자동 생성
```

## 6. 데이터 및 입력

| 입력 | 형식 | 비고 |
|------|------|------|
| 회사 QA 표준 | Markdown/PDF | Claude Project 학습 |
| 테스트 케이스 양식 | Markdown/Excel | 회사 템플릿 |
| 과거 이슈 이력 | CSV/Markdown | 익명화 권장 |
| 기능 명세서 | Markdown/PRD | 입력 |
| 이슈 raw 텍스트 | 텍스트 | 사용자 신고·내부 메모 |

## 8. 제약사항

| 제약 | 대응 |
|------|------|
| 기능 명세 외부 업로드 정책 | 익명화/요약 후 학습, 기밀 정보 분리 |
| 자동화에 의존 시 누락 위험 | "AI는 보조" 정책 명문화, 고위험 기능은 사람 우선 |
| 회사 우선순위 기준 차이 | 회사 정책 문서 학습 단계 필수 |

## 9. 검증

```
AI 생성 테스트 케이스
   ↓
QA 담당자 검토
   ├─ 누락 시나리오 보강
   ├─ 우선순위 조정
   └─ 환경별 차이 보완
   ↓
실행 → 결과 기록
   ↓
실제 발생 이슈 vs 예측 시나리오 비교
   ↓
프롬프트·체크리스트 보강
```

**누락된 시나리오가 운영 사고로 이어진 경우** → 사례를 Claude Project Knowledge에 추가하여 다음부터 자동 검출되도록 학습.

## 10. Non-Goals

| 항목 | 이유 |
|------|------|
| 자동 테스트 실행 | 별도 자동화 도구 영역 (Selenium·Playwright) |
| 코드 레벨 단위 테스트 작성 | 개발자 영역, 비개발자 워크숍 범위 외 |
| 부하·보안 테스트 자동화 | 전문 도구·전문성 필요 |
| 사용자 신고 자동 응답 | 프로젝트 #1 (CS 에이전트)에서 처리 |

## 11. 확장 가능성

- **버그 리포트 자동 발행**: 이슈 카드를 GitHub/Jira 이슈로 자동 등록 (gh CLI 활용)
- **회귀 테스트 자동 생성 강화**: 코드 diff와 연동하여 변경 영향 분석 (개발자 협업 필요)
- **QA 메트릭 대시보드**: 누적 이슈·테스트 케이스로 품질 추이 시각화
- **CS 에이전트 연계 (프로젝트 #1)**: CS에서 발견된 버그를 QA 이슈 카드로 자동 전환
