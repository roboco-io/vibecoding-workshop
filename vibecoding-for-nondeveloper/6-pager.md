# 비개발자를 위한 바이브 코딩 워크숍

**비개발자 대상 | 10~15명 | 반나절**

---

## 1. 서론: AI를 쓰고 있지만, 제대로 쓰고 있지 않다

비개발자 대상 사전 설문을 실시하면, 놀라울 정도로 일관된 패턴이 나타난다. 대다수가 거의 매일 또는 하루 여러 번 AI를 사용하고 있다. Claude, ChatGPT, Gemini — 복수의 AI 도구를 목적에 따라 전환하며 쓰는 멀티-AI 사용자가 대부분이다. AI가 낯선 사람들이 아니다.

그러나 80% 이상이 "결과 품질이 들쑥날쑥하다"고 답하고, 절반 이상이 "결국 내가 다 고쳐야 한다"고 한다. AI가 초안을 만들면 사람이 대대적으로 수정하는 비효율적 루프에 갇혀 있다. AI를 쓰는데 생산성이 체감되지 않는 역설적 상황이다.

이 워크숍은 AI 입문 교육이 아니다. 이미 AI를 쓰고 있는 사람들에게 **AI를 믿을 수 있게 만드는 법**을 가르친다. 프롬프트를 정교하게 다듬고, 결과물을 체계적으로 검수하고, 최종적으로 코딩 없이 자연어만으로 실제 동작하는 결과물을 만드는 전 과정을 경험하게 한다.

---

## 2. 참가자: 문서를 다루는 지식 노동자, AI의 가장 큰 수혜 대상

이 워크숍의 대상은 영업·CS·운영, 기획/PM, 디자인, 경영지원 등 비개발 직군이다. 코딩 경험이 전혀 없는 사람이 약 40~50%, "따라 해본 적 있는" 수준까지 포함하면 과반이 코드 작성 경험이 거의 없다.

그러나 이들의 주요 업무 산출물을 보면, 문서(기획·제안·보고)가 압도적이다. 고객 응대/CRM, 스프레드시트, 노코드 툴이 뒤를 잇는다. 본질적으로 문서와 데이터를 다루는 지식 근로자 그룹이다. 이것은 AI가 가장 즉각적인 가치를 만들어낼 수 있는 업무 영역이다.

가장 시간을 잡아먹는 반복 업무를 물으면, 참가자 거의 모두가 서로 다른 답을 한다. 문의 분류, PRD 작성, 경쟁사 리서치, 예산 수정, 통계 추이 분석, 목업 제작 — 병목이 개인마다 고유하다. 이 발견은 워크숍 설계에 결정적 영향을 미쳤다. 단일 템플릿 실습이 아니라, **각자의 업무에 즉시 적용할 수 있는 범용 패턴**을 가르쳐야 한다.

워크숍에서 얻고 싶은 결과 1순위는 반복 업무 자동화이고, 성공 기준 1순위는 "작업 시간 50% 이상 단축"이다. 도구·앱 만들기보다 업무 시간 절감이 압도적으로 높다. 이 그룹의 핵심 니즈는 기술 구현이 아니라 **생산성 향상**이다.

---

## 3. 워크숍 구조: 문제 정의에서 개발 계획까지, 코딩 없이

워크숍은 6단계로 구성된다. 환경설정을 제외한 모든 단계에서 참가자는 코드를 직접 작성하지 않는다. 자연어로 클로드에게 지시하고, 결과물을 검토하고, 피드백을 주는 것이 참가자의 역할이다.

### 0단계: 환경설정

클로드 코워크 모드가 환경설정의 핵심이다. 참가자가 "저는 비개발자입니다. 다음 도구들을 설치해야 합니다"라고 말하면, 클로드가 이미 설치된 것을 확인하고 필요한 것만 순서대로 설치를 진행한다. 코드 CLI, Git CLI, GitHub CLI, VSCode — 이 도구들을 비개발자가 직접 설치 명령어를 입력할 필요가 없다.

비개발자 그룹은 개발자보다 로컬 도구 설치 제약이 오히려 낮은 경우가 많다. 다만 Windows 사용자 비율이 높으므로, 경로 설정 등 OS 특화 안내가 필요하다.

### 1단계: 문제 정의 — 채팅으로 브레인스토밍

클로드 앱의 채팅 모드를 사용한다. 참가자는 자기 업무에서 가장 시간이 많이 걸리는 반복 업무를 가져온다. "저는 [직무]를 담당하고 있습니다. 매일 반복하는 [업무]를 AI로 자동화할 수 있는 방법을 함께 고민해주세요." 클로드와 대화하며 문제를 구체화하고, 해결 방안을 탐색하고, MVP 범위를 정한다.

강사가 먼저 데모를 진행한 뒤, 참가자가 각자의 문제로 따라한다. 참가자마다 병목이 다르기 때문에, 동일한 패턴(역할+맥락+출력형식 지정)으로 서로 다른 문제를 풀게 된다. 대화가 끝나면 마크다운으로 다운로드하여 다음 단계의 입력으로 사용한다.

### 2단계: PRD 작성 — 심층 인터뷰

클로드 앱의 코드 모드로 전환한다. 1단계에서 만든 아이디어 문서를 프로젝트 폴더에 넣고, 클로드에게 심층 인터뷰를 요청한다. "한 번에 모든 질문을 하지 말고, 한 가지 주제씩 순서대로 물어봐주세요." 사용자가 누구인지, 핵심 기능과 우선순위는 무엇인지, 성공 기준은 어떻게 되는지, 제약 조건은 무엇인지 — 클로드의 질문에 답하는 것만으로 PRD가 완성된다.

이 단계가 중요한 이유는 두 가지다. 첫째, 비개발자가 "무엇을 만들어야 하는지"를 체계적으로 정리하는 경험을 한다. 둘째, AI에게 "해줘"가 아니라 **"나에게 질문해줘"** 로 시작하는 인터뷰 퍼스트 패턴을 체화한다. 대다수가 겪는 "결과 품질 불안정" 문제의 근본 원인은 불충분한 맥락 전달이고, 심층 인터뷰가 그 해결책이다.

### 3단계: 목업 제작 — 아티팩트와 코드

PRD를 클로드 앱 채팅의 아티팩트 기능에 붙여넣어 시각적 목업을 생성한 뒤, 코드 모드에서 실제 동작하는 HTML 목업으로 구현한다. "PRD에 기반해서 동작하는 HTML 목업을 만들어줘. 랄프 루프를 사용해서 끝까지 완성해줘." 클로드가 스스로 결과를 검토하고, 부족한 부분을 발견하면 자동으로 수정하는 반복 과정을 거쳐 완성도 높은 결과물이 나온다.

비개발자가 브라우저에서 자신이 정의한 문제의 해결책을 실제로 보는 순간은 이 워크숍의 가장 강력한 체험 포인트다. 코드를 한 줄도 쓰지 않았는데, 동작하는 프로토타입이 눈앞에 있다.

### 4~6단계: 개발 계획, 아키텍처 문서, 튜토리얼

4단계에서 개발 계획을 수립하고 GitHub 이슈로 등록한다. 각 이슈에는 작업 배경, 작업 내용, 인수 조건, 의존성이 포함된다. 비개발자가 개발자에게 작업을 넘길 때 필요한 모든 정보가 체계적으로 정리된다.

5단계에서 Mermaid 다이어그램으로 아키텍처를 시각화하고 README를 업데이트한다. 6단계에서 오늘 진행한 전체 과정을 비개발자용 바이브 코딩 튜토리얼로 정리하고, 클로드 코드 프롬프트 중심의 Git 매뉴얼을 만든다.

## 4. 핵심 설계 원칙: "코딩 없이"는 타협이 아니라 전략이다

비개발자 워크숍에서 코딩을 배제한 것은 난이도를 낮추기 위한 타협이 아니다. 세 가지 전략적 판단에 기반한다.

**첫째, 참가자의 니즈가 코딩이 아니다.** 비개발자 설문에서 워크숍에 기대하는 결과 1순위는 반복 업무 자동화이고, 도구·앱 만들기는 하위권에 머문다. 이들이 원하는 것은 기술 역량이 아니라 업무 시간 절감이다.

**둘째, 바이브 코딩의 핵심이 "코딩 없이 만드는 것"이다.** 자연어로 의도를 전달하고, AI가 구현하고, 사람이 검수하는 — 이것이 바이브 코딩의 정의다. 비개발자야말로 바이브 코딩의 가장 순수한 실천자다. 코드를 읽을 수 없기 때문에 오히려 "자연어 → AI → 결과물 → 검수" 루프에 더 충실하게 된다.

**셋째, 검수 루프가 코딩보다 중요하다.** 비개발자의 AI 사용 최대 고충은 결과 품질 불안정과 재작업 부담이다. 이 문제의 해결책은 더 나은 코드가 아니라 더 나은 프롬프트와 검수 과정이다. 역할·맥락·출력형식을 명확히 지정하고, 결과물을 단계적으로 검토하고, 피드백으로 반복 개선하는 패턴 — 이것은 코딩 능력과 무관한 스킬이다.

워크숍의 4가지 핵심 패턴은 모두 이 원칙 위에 설계되었다. **역할+맥락+출력형식 지정**(명확한 요청), **심층 인터뷰**(AI 주도 질문), **검수 루프**(반복 개선), **트러블슈팅**(문제 해결). 이 패턴들은 오늘 워크숍뿐 아니라 내일 업무에서도 그대로 적용 가능하다.

## 5. 도구 전략: 클로드 앱의 4가지 모드를 상황에 맞게

개발자 워크숍이 Claude Code CLI + OMC + OpenSpec + GitHub CLI를 사용하는 반면, 비개발자 워크숍은 **클로드 앱 하나**를 중심으로 운영된다. 같은 도구지만 4가지 모드(채팅·코드·코워크·아티팩트)를 상황에 맞게 전환하여 사용한다.

| 모드 | 용도 | 사용 단계 |
|------|------|-----------|
| **채팅** | 대화, 브레인스토밍, 질문 | 1단계: 문제 정의 |
| **코드** | 파일 생성·수정, 코드 실행 | 2단계: PRD, 4~6단계: 계획·문서 |
| **코워크** | 컴퓨터 작업 대행 | 0단계: 환경설정 |
| **아티팩트** | UI 목업, 다이어그램 | 3단계: 목업 제작 |

코드 CLI와 GitHub CLI도 사용하지만, 참가자가 명령어를 외울 필요는 없다. 클로드 코드 모드에서 "변경사항을 커밋하고 GitHub에 푸시해줘"라고 자연어로 요청하면 된다. 기술적 복잡도는 AI가 흡수하고, 참가자는 의사결정에 집중한다.

기업 환경에서는 상당수의 참가자가 실제 업무 데이터를 AI에 업로드할 수 있는지 불확실하거나 불가능한 상태일 수 있다. 이에 대비하여 익명화된 샘플 데이터셋을 사전 준비하고, 실제 데이터 대신 더미 데이터로 실습할 수 있는 시나리오를 설계한다.

## 6. 성공 기준과 기대 효과

### 워크숍 성공 기준

| 기준 | 목표 |
|------|------|
| PRD 문서 완성 | 참가자 100% |
| 동작하는 HTML 목업 생성 | 참가자 80% 이상 |
| GitHub 이슈 기반 개발 계획 등록 | 참가자 80% 이상 |
| 4가지 핵심 패턴 체험 (역할지정, 인터뷰, 검수루프, 트러블슈팅) | 참가자 100% |
| "내일 업무에 바로 적용할 수 있다"는 자기 평가 | 참가자 80% 이상 |

### 리스크와 대응

**코딩 경험 격차**: 약 40~50%는 코딩 경험이 전혀 없고, 일부는 코드·쿼리를 조금 수정할 수 있다. 단일 트랙으로 운영하되, 기술 친화 그룹에게는 "심화 응용 힌트"를 별도 제공한다. 커리큘럼 자체는 코딩 경험이 없는 다수를 기준으로 설계한다.

**Windows 환경**: 비개발자 그룹은 Windows 사용 비율이 높다. 코드 CLI 경로 설정, 터미널 접근 등 OS 특화 안내를 사전 체크리스트에 포함한다.

**진도 차이**: "완주보다 깊이"가 이 워크숍의 원칙이다. 6단계를 모두 끝내지 못해도, 현재 단계에서 패턴을 체화하는 것이 목적이다.

### 기대 효과

이 워크숍을 마치면, 비개발자 참가자는 세 가지를 가지고 돌아간다. 첫째, 자기 업무 문제를 AI와 함께 정의하고 해결 방안을 설계하는 **구체적 경험**. 둘째, 어떤 업무에든 적용할 수 있는 4가지 **프롬프트 패턴**. 셋째, 개발자에게 넘길 수 있는 PRD·목업·이슈 기반 개발 계획이라는 **실제 산출물**.

비개발자 워크숍의 핵심 기대치는 "작업 시간 50% 이상 단축"이다. 이 워크숍이 그 기대에 부응하려면, 오늘 배운 패턴이 내일 업무에서 바로 작동해야 한다. 그래서 실습 주제가 가상의 프로젝트가 아니라 참가자 자신의 업무 문제다.

---

**한 줄 요약**: AI를 매일 쓰지만 "결국 다 고쳐야 하는" 비개발자에게, 코딩 없이 자연어만으로 문제를 정의하고 해결책을 설계하고 동작하는 결과물을 만드는 전 과정을 직접 체험하게 한다.
